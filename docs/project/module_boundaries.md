# 폴더와 모듈 경계

## 목적

`DEV-0002`부터 사용하는 Godot 소스 폴더와 각 모듈의 책임을 고정한다. 새 파일을 만들 때 어느 폴더에 둘지 판단하고, 화면·저장·게임 규칙이 서로의 책임을 가져가지 않도록 하는 개발 기준이다.

이 문서는 코드 배치와 의존 방향만 소유한다. 실제 게임 규칙은 관련 `confirmed` Design 문서가, 제품과 시스템 연결은 GDD가 소유한다.

## 실제 폴더 구조

```text
res://
  src/
    app/
    core/
    gameplay/
    harness/
    meta/
    infrastructure/
    ui/
    data/
  tests/
```

동결 개발 제안서의 `App`, `Core`, `Gameplay`, `Meta`, `Infrastructure`, `UI`, `Data`, `Tests`를 Godot 경로 관례에 맞춰 소문자로 배치했다. 현재 GDD가 하네스를 독립 시스템으로 구분하므로 `src/harness/`도 함께 둔다.

이번 티켓은 위 최상위 경계만 만든다. 각 모듈 안의 기능별 하위 폴더는 실제 기능 티켓에서 필요한 것만 추가한다.

## 모듈별 책임

| 경로 | 맡는 책임 | 맡지 않는 책임 |
|---|---|---|
| `res://src/app/` | 부팅, 장면 흐름, 전역 게임 상태, 모듈 조립 | 탐험·경제 규칙 계산, 화면 표시 세부 |
| `res://src/core/` | 안정적 ID 기반, 이벤트, 시간, 여러 모듈이 공유하는 최소 타입 | 특정 기능의 규칙, 장면과 UI |
| `res://src/gameplay/` | 플레이어, 탐색, 상호작용, 위험, 인벤토리, 회수와 탈출 | 거점 경제, 화면 전환, 저장 입출력 |
| `res://src/harness/` | 하네스 모듈, 충전, 분석, 작업과 비상 행동 | 하네스 세부 규칙의 임의 확정, 일반 탐험 흐름 |
| `res://src/meta/` | 거점, 경제, 감정, 연구, 장비와 성장 | 탐험 조작, 저장 파일 처리, 화면 그리기 |
| `res://src/infrastructure/` | 저장, 설정, 입력, 오디오, 현지화와 로그의 기술 연결 | 실패 손실·가격·진행처럼 게임이 결정할 규칙 |
| `res://src/ui/` | 타이틀, HUD, 지도, 인벤토리, 거점, 정산과 옵션 표시·사용자 명령 전달 | 게임 규칙 계산, 저장 처리, 직접 장면 전환 |
| `res://src/data/` | 아이템·방·루트·위험·경제·텍스트의 정의와 콘텐츠 값 | 실행 중 상태 변경, 화면 흐름, 저장 시점 결정 |
| `res://tests/` | 단위·통합·스모크 검사와 테스트 전용 자료 | 출시 게임 기능과 실제 콘텐츠 |

`src/harness/`는 GDD에 확정된 하네스 행동과 충전을 구현한다. [`harness_engineering.md`](../design/harness_engineering.md)는 DEV-0408에서 요구와 미적용 비교안을 정리했으며 `draft`를 유지한다. 미정인 장착·해금·성장 수치를 확정된 규칙으로 추정해 구현하지 않는다. GDD·기존 결정과 함께 읽고 해당 구현 작업의 시험 범위를 먼저 기록한다.

## 의존 방향

1. `core`는 다른 프로젝트 모듈을 참조하지 않는다.
2. `data`는 공통 ID나 타입이 필요할 때 `core`만 참조한다.
3. `gameplay`, `harness`, `meta`는 `core`와 `data`의 공개 정의를 사용한다. 서로 협력할 때는 공개 명령·상태·이벤트를 통하고 상대 모듈의 내부 파일을 직접 조작하지 않는다.
4. `infrastructure`는 전달받은 상태를 읽고 쓰는 기술 처리를 맡는다. 게임 규칙 모듈은 구체적인 저장·입력·오디오 구현을 직접 만들지 않고 `app`에서 연결한다.
5. `ui`는 공개 상태를 표시하고 사용자 명령을 전달할 수 있지만 결과를 계산하거나 장면을 직접 바꾸지 않는다.
6. `app`은 모듈을 조립하고 중앙 상태·장면 흐름을 관리한다. 여러 모듈을 연결해야 하는 조정 코드는 `app`에 둔다.
7. `tests`는 필요한 모듈을 참조할 수 있지만 출시 코드에서는 `tests`를 참조하지 않는다.
8. 순환 의존은 만들지 않는다. 두 모듈이 서로를 필요로 하면 공유 정의를 `core`로 옮기거나 조정을 `app`에 둔다.

## 파일 배치 판단 순서

새 파일을 추가할 때 다음 순서로 위치를 정한다.

1. 하나의 기능 규칙이면 그 기능을 소유한 `gameplay`, `harness`, `meta`에 둔다.
2. 저장·입력·오디오처럼 엔진이나 운영체제와 연결하는 코드면 `infrastructure`에 둔다.
3. 표시와 사용자 명령 전달이면 `ui`에 둔다.
4. 콘텐츠 정의나 조정 가능한 값이면 `data`에 둔다.
5. 여러 모듈을 연결하거나 화면 흐름을 바꾸면 `app`에 둔다.
6. 둘 이상에서 정말 같은 의미로 쓰는 최소 정의만 `core`에 둔다. 편의를 위해 기능 코드를 `core`로 옮기지 않는다.

## 개발 진행과 인계

- `DEV-0002`에서 위 9개 경계를 만들고 각 폴더는 `.gitkeep`만 둔 상태로 시작했다.
- `DEV-0003`에서 `src/app/`에 `GameState` Autoload와 최소 조립 장면을, `src/ui/`에 개발용 상태 표시 UI를 추가했다.
- `GameState`만 현재 상태와 허용 전환을 바꾸며, 메인 장면의 UI는 공개 전환 인터페이스에 요청만 보낸다.
- `DEV-0004`에서 `src/infrastructure/input_actions.gd`가 행동 이름과 Godot 입력 조회를 소유하고, `project.godot`이 키보드·마우스 기본 연결을 소유하도록 했다.
- 게임 규칙과 UI는 실제 키 코드를 참조하지 않고 `InputActions`의 공개 행동 이름과 조회 API만 사용한다.
- `DEV-0005`에서 `src/core/stable_id.gd`는 여러 모듈이 공유할 최소 ID 검증만 소유하고, `src/data/`는 공통 콘텐츠와 아이템 데이터 정의를 소유하도록 했다.
- 표시 이름과 안정적 ID는 `ContentDefinition`의 독립 필드이며 `ItemDefinition`에는 실행 중 획득 상태나 저장 상태를 두지 않는다.
- `DEV-0006`에서 `src/infrastructure/game_log.gd`는 엔진 로그 연결과 공통 형식을, `src/app/dev_entry.gd`는 개발 상태 진입 조정을 소유하도록 했다.
- `tests/smoke/`는 출시 장면이 참조하지 않는 상태 전환 스모크 장면을 소유하며 종료 코드로 결과를 전달한다.
- `DEV-0006` 완료 뒤 정합성 검사에서 위 경계와 프로젝트 기반이 일치함을 확인했고, 2026-08-01 사용자의 진행 지시에 따라 G0를 통과했다.
- `DEV-0101`에서 `src/gameplay/player/`가 `CharacterBody2D` 기반 플레이어 이동과 자식 `Camera2D`를 소유하도록 했다. 이동 입력은 `InputActions`의 공개 조회 API를 사용하며, `DEV-0307`에서 적재 단계와 감속 데이터 조회를 연결했다.
- `tests/fixtures/`는 이동·카메라와 일시정지를 직접 확인하는 개발 공간을, `tests/smoke/`는 실제 플레이어 장면을 자동 검증하는 장면을 소유한다. 테스트 공간의 일시정지 조작은 출시 플레이 흐름이 참조하지 않는다.
- `DEV-0102`에서 `src/gameplay/interaction/`이 공통 대상 인터페이스, 대상 감지와 상호작용 실행을 소유하도록 했다. 플레이어 장면은 감지기와 실행기를 조립하고 실제 입력 키 대신 `InputActions.INTERACT`를 사용한다.
- `src/ui/interaction_prompt.*`는 현재 대상의 안내 문구만 표시하며 대상 선택이나 상호작용 결과를 결정하지 않는다. 시험용 회수품과 문은 같은 `Interactable` 인터페이스를 사용한다.
- `tests/fixtures/interaction_test_space.tscn`은 수동 확인 공간을, `tests/smoke/interaction_system_smoke.tscn`은 감지·안내·실행과 두 대상의 공통 인터페이스 검증을 소유한다.
- `DEV-0103`에서 `src/gameplay/inventory/`가 실행 중 아이템 목록, 슬롯·무게 합계와 단계, 선택·버리기 규칙을 소유하도록 했다. 시험용 회수품은 공개 `PlayerInventory` 명령으로 획득을 요청하며 슬롯 한도 거절 여부를 직접 결정하지 않는다.
- `src/ui/inventory_panel.*`는 공개 인벤토리 상태를 표시하고 열기·닫기·일반 버리기 명령을 전달한다. 슬롯·무게 규칙은 계산하지 않으며 `DEC-103`에 따라 화면이 열린 동안 `SceneTree` 일시정지만 제어한다.
- `tests/fixtures/inventory_test_space.tscn`은 시험용 한도·무게 값으로 직접 확인할 공간을, `tests/smoke/inventory_system_smoke.tscn`은 획득·한도 거절·무게 단계·화면 표시·버리기와 일시정지를 자동 검증하는 장면을 소유한다. 출시 코드는 이 테스트 값과 장면을 참조하지 않는다.
- `DEV-0104`에서 `src/gameplay/recovery/`가 인벤토리에서 전달받은 현재 회수품 목록과 예상 가치 합계를 고정하도록 했다. 실제 판매·비용·순이익 계산은 `meta`의 후속 책임으로 남겨 둔다.
- `src/ui/item_value_text.gd`는 예상 가치 범위와 비화폐 보상 문구를, `src/ui/recovery_result_panel.*`는 회수품별 가치와 결과 합계 표시를 소유한다. UI는 포함 물품이나 합계를 결정하지 않는다.
- `tests/fixtures/recovery_result_test_space.tscn`은 회수 결과 표시를 직접 확인하는 공간을, `tests/smoke/recovery_result_smoke.tscn`은 들고 나온 물품만 포함되는지와 가치 합계·비화폐 보상 분리를 자동 검증하는 장면을 소유한다.
- `DEV-0105`에서 `src/gameplay/hazards/`가 위험 대상의 사전 징후, 경고 상태, 안정화 가능 여부, 붕괴와 범위 안 포착 이벤트를 소유하도록 했다. 실제 피해·부상·실패 판정은 이 모듈이 임의로 결정하지 않는다.
- `src/harness/harness_controller.gd`는 플레이어의 공개 위험 감지 결과를 받아 `use_harness` 입력, 시험 충전과 안정화 명령을 소유한다. `DEV-0110`에서 정밀 분석·비상 방전과 공통 충전 처리를 확장했다. 위험은 하네스 내부 상태를 직접 바꾸지 않으며 하네스는 대상의 공개 조회·명령만 사용한다.
- `src/ui/harness_status.*`는 현재 충전·기본 분석·구매한 정밀 분석과 `Q` 행동을 표시하고 분석 버튼을 공개 명령에 연결한다. 버튼 활성 여부도 하네스에 조회하며 충전 소모와 대상 규칙을 결정하지 않는다.
- `tests/fixtures/hazard_harness_test_space.tscn`은 사전 징후와 `Q` 안정화를 직접 확인하는 공간을, `tests/smoke/hazard_harness_smoke.tscn`은 안정화와 미대응 분기를 자동 검증하는 장면을 소유한다. 충전·비용·경고 시간은 테스트와 장면에서 조정하는 시제품 값이다.
- `DEV-0106`에서 `src/gameplay/recovery/`가 입구 생환 명령, 탐험의 단일 종료 상태와 생환·실패 결과를 소유하도록 했다. `PlayerInventory`는 현재 탐험 물품을 공개 명령으로 인계하고 비우며, 회수 모듈은 생환 물품만 기존 `RecoveryResult`에 넣는다.
- `src/gameplay/recovery/entrance_exit.*`는 공통 `Interactable`을 통해 활성 탐험의 생환만 요청한다. 위험 모듈은 계속 포착 이벤트만 내며, 시험 공간의 조립 코드가 이 공개 이벤트를 탐험 실패 명령에 연결한다.
- `src/ui/exploration_outcome_panel.*`은 생환의 회수 결과와 실패의 손실 개수를 표시할 뿐 종료 상태, 포함 물품이나 손실을 결정하지 않는다.
- `tests/fixtures/exploration_end_test_space.tscn`은 입구 생환과 위험 포착 실패를 직접 확인하는 공간을, `tests/smoke/exploration_end_smoke.tscn`은 두 종료 분기, 물품 인계·손실과 종료 상태 잠금을 자동 검증하는 장면을 소유한다.
- `DEV-0107`에서 `tests/fixtures/core_loop_playtest_space.tscn`이 기존 공개 모듈을 안전 경로·위험 보상 경로가 있는 작은 던전으로 조립했다. 시험용 아이템·슬롯·무게·가치·하네스 충전과 경고 시간은 `tests` 안에만 있으며 출시 코드와 제품 데이터가 참조하지 않는다.
- `tests/smoke/core_loop_playtest_smoke.tscn`은 같은 플레이테스트 장면으로 안전 생환, 위험 대응과 적재 교체 뒤 생환, 미대응 실패를 자동 검증한다. 테스트 조립 코드는 모듈 내부 상태를 직접 바꾸지 않고 공개 명령·상태·이벤트를 사용한다.
- `DEV-0108`에서 `src/gameplay/inventory/inventory_item.gd`가 불변 아이템 정의와 현재 탐험의 감정 여부를 분리한다. `ItemDefinition`에는 실행 중 상태를 추가하지 않으며 `PlayerInventory`와 회수 모듈은 공개 실행 중 물품 상태를 전달한다.

### DEV-0318의 후속 생존 상태 검토

이번 작업은 실행 모듈을 추가하지 않는다. [생존 규칙 검토안](../design/survival_rules.md)은 `draft`이며 다음 책임 분리를 제안한다. 위험 소유자는 경고·접촉/작동 판정·주기별 중복 방지, 향후 생존 상태 소유자는 건강 잔량·일시적 부상·일회성 행동 불능, 플레이어/상호작용 계층은 공개된 행동 효율의 적용을 담당한다. 실패·회수품 제거·정산 전달은 기존 `ExplorationRun`과 앱 흐름에 둔다. HUD가 피해·회복·실패를 결정하거나 거점 저장이 탐험 도중의 생존 상태를 소유하게 하지 않는다.

현재 `PlayerController`는 적재 계수만 적용하고 `InteractionController`는 E 입력을 즉시 처리한다. 건강·부상/이동/HUD와 조사·회수 시간을 별도 작업으로 나누는 이유는 새 시간·취소·중복 회수 계약을 기존 조작 전체에 섞지 않기 위해서다. 퇴로 변화의 실제 통로 판정과 마지막 관찰 정보의 UI 책임도 분리한다. 다음 작업 순서·범위와 완료 검사는 [개발 인계](development_handoff.md#dev-0318--생존-규칙과-시제품-범위-정리)를 따른다. 이 절은 아직 존재하지 않는 클래스·저장 필드의 구현 완료를 뜻하지 않는다.

### DEV-0319의 건강·부상 상태와 HUD

- `src/data/survival_rule.gd`와 `prototype_survival.tres`는 유효 범위와 건강 2·함정 피해 1·부상 6초·이동 0.9의 시험 데이터를 소유한다. 실행 시 복사하므로 원본 자원의 변경이 진행 중 출정에 섞이지 않는다.
- `src/gameplay/player/player_survival.gd`는 출정 수명·건강 잔량·부상 시간·이동 계수와 한 번의 행동 불능 신호를 소유한다. 피해를 받는 위치·경고·같은 함정 주기의 중복 판정이나 물품 손실·저장을 소유하지 않는다.
- `PlayerController`는 현재 출정에서 선택적으로 연결한 생존 계수와 적재 계수를 곱해 실제 이동에 적용한다. 생존 계수를 연결하지 않은 기존 비교 장면은 이전 이동을 유지한다. 이동 소음 소유권과 무게 단계는 바꾸지 않는다.
- `PrototypeExploration`은 함정 입력을 일반 피해로, 골렘 포착·붕괴를 행동 불능으로 연결하고 기존 `ExplorationRun`에 실패를 전달한다. 종료 뒤 생존 상태를 잠그고 HUD는 공개 조회만 사용한다. 함정 분석은 현재 출정에서 건강 피해 안내를 선택하며 기존 장면의 안내는 유지한다.
- `ExplorationOutcomePanel`은 `trap_damage` 원인으로 건강 소진을 설명한다. 원인과 생존 상태를 거점 저장 필드로 추가하지 않는다. 재출정에서는 새 구성 요소가 새 상태를 만든다.
- `tests/smoke/player_survival_smoke.*`는 데이터·수명·실제 이동/소음/메뉴/버리기·함정 재진입·Q·종료 경합·화면·앱 실패/저장/새 출정을 검사한다. 기존 함정 검사는 현재 출정에서 첫 피해 생존·다음 주기 실패로 갱신했다.

DEV-0318 절은 당시 검토 이력이다. 현재 상태·이동·HUD의 적용 범위는 [생존 시험 적용 기록](../design/survival_rules.md#dev-0319-시험-적용-범위)을 따른다. `InteractionController`의 즉시 E와 조사·회수 시간의 후속 분리는 유지한다.

### DEV-0320의 조사·회수 시간

- `PrototypeExploration`은 현재 출정에서 시간 기능을 구성하고 시작/종료·가방/지도 취소를 연결한다. 기존 `InteractionPrompt`는 공개된 진행 문구만 표시하며 부상 HUD는 공개 효율을 읽는다. 문·입구·Q·G와 기존 저장 모듈의 책임은 유지한다.

DEV-0318~DEV-0319의 즉시 E·후속 상호작용 문구는 당시 이력이다. 현재 적용 범위는 [DEV-0320 시험 기록](../design/survival_rules.md#dev-0320-조사회수-시간-시험-적용)을 따른다.

### DEV-0405의 수리 구현 전 책임 검토

[수리 검토안](../design/repair_rules.md)의 현재 코드 대조는 후속 구현 계약이다. 새 실행 파일·폴더를 만든 것이 아니다. 내구 상태·수리 견적/안전망의 판단은 `meta`, 손상·단가 후보 데이터는 `data`, 후보 저장 후 교체와 서비스/출정 상호 배제는 `app`, 상태·비용/잔액 확인·취소 표시는 `ui`, 저장 버전 전환은 `infrastructure`의 기존 책임을 따른다. 탐험 결과는 손상 판단에 필요한 종료 정보를 공개하고 UI가 피해·수리비를 계산하지 않는다. 실제 타입·필드·파일명은 DEV-0406과 후속 수리 작업에서 정한다.

### DEV-0408의 하네스 준비·성장 후속 구현 경계

이번 작업은 문서 정리이며 실행 모듈·클래스·저장 키를 추가하지 않았다. 다음 장착 구현은 기존 경계를 따라 `meta`가 거점 선택/해금 조건·후보, `data`가 명시적인 행동 대응·한도/조건, `core`의 출정 구성이 검증된 복사본, `harness`가 실제 사용 권한/공유 충전, `app`이 저장 후 상태 교체와 출정 전달, `ui`가 설명/선택/확인, `infrastructure`가 저장 입출력을 맡도록 분리한다. 구체적인 파일/필드는 해당 구현 작업에서 정한다.

`DoorHoldTarget`이 `StabilizableHazard`를 상속한다고 설계상 문 고정을 안정화 모듈에 자동 귀속하지 않는다. 함정/잔해·잔여 구역 입구·문 고정·골렘과 각 행동의 대응을 데이터/공개 인터페이스로 명시하고 실제 실행 경로에서 확인한다. `commit_charge_action`을 사용하는 별도 비상 탈출, 별도 횟수의 `NoiseLureController`는 첫 장착 비교의 적용 여부를 명시해 기존 기능의 우발적 차단을 막는다. 입력/UI만 숨겨 사용 권한을 구현하지 않는다.

영구 해금·거점 장착·런 구성과 충전·영구 내구는 책임을 구분한다. 장착 변경이 하네스 재생성·무료 수리·런 충전 초기화로 이어지지 않게 한다. DEV-0408 당시 `ProgressStore` 스키마 3·6필드는 유지했으며 후속 확장은 구형 기본 구성·검증·읽기 보존/정상 저장 전환을 함께 설계한다. [검토안](../design/harness_engineering.md)과 Q-024·Q-025는 단독 구현 권한이 아니다.

### DEV-0409의 장착 선택·출정과 저장 경계

### DEV-0410의 영구 개선 후속 구현 경계

이번 작업은 [미적용 설계 제안](../design/harness_engineering.md#dev-0410-영구-성장-제안--미적용)과 검사 계약만 정리했으며 실행 모듈을 추가하지 않았다. 현재 쓰기 스키마 4·7필드와 DEV-0409 출정/장착을 유지한다.

- `meta`는 구매 자격·견적·결제/보유 후보와 기존 서비스 복사에서의 보존을, `data`는 개선별 ID·가격·상한·효과 값을 맡는다. 구체적인 파일/ID·확장 버전은 DEV-0411 착수에서 기록한다.
- `core`는 출정 시 장착+보유 개선 복사본을 전달한다. `harness`는 모듈 장착/개선 자격·분석 유효 구간·공유 충전을 검사하고 `gameplay`의 공개 상태/타이머 조회와 효과 적용 경계를 사용한다. `ui`가 대상의 비공개 타이머나 저장 파일을 직접 읽어 계산하지 않는다.
- 현재 `HarnessController`는 정밀 정보 문자열을 비교해 분석 만료를 판정한다. 남은 초를 이 문자열에 단순 추가하면 매번 분석이 만료된다. 유효 대상/상태와 동적 표시를 분리하되 대상/상태/범위 변경의 기존 만료 계약을 보존해야 한다. 같은 상태의 타이머 재시작은 남은 시간 조회에 반영한다.
- 골렘/문은 출정의 개선 값으로 해당 행동의 지속시간을 계산한다. 공유 Resource나 기본값을 누적 변경하거나 반복 명령으로 시간을 더하지 않는다. 과거 G1 기준 장면·별도 E 탈출·소음 유인의 적용 범위를 유지한다.
- `app`은 구매·저장 성공 후 거점 교체/출정 전달과 서비스 상호 배제를, `infrastructure`는 스키마 검증·구형 보완·읽기 원본 보존을 맡는다. `ui`는 가격/잔액·보유/장착별 효과·취소/확인/실패만 표시한다. 테스트는 고립한 경계와 실제 앱 경제 순환을 구분하고 신규 실행 근거를 새 작업 기록에 남긴다.

### DEV-0411의 영구 개선 구매·발견 경계

- `HarnessUpgradeRule`/`prototype_harness_upgrades.tres`가 두 내부 ID·가격·효과·보유 목록 검증을 맡는다. `HarnessUpgradeQuote`는 거점 원본 상태와 가격/효과 복사본을 보관한다. `HubState`는 구매 재검증·후보 차감/보유와 정산 발견 병합을 맡고, 기존 서비스의 복사에서도 보유를 유지한다.
- `ExpeditionLoadout.harness_upgrades`는 보유 ID의 독립 복사본이다. `HarnessController.configure_modules`가 장착과 보유를 확인해 개선 값을 런에 한 번 고정한다. 정적 유료 정보/상태 변경 번호와 동적 남은 시간 표시를 분리한다. `StabilizableHazard`·잔해·골렘의 공개 상태/타이머 조회를 사용하고 UI가 비공개 타이머를 직접 읽지 않는다. 문/골렘에 행동별 보너스를 전달하고 공유 Resource를 변경하지 않는다.
- `HarnessUpgradeDiscovery`는 기본 앱 선택 구역의 E 조사·소유 여부에 따른 발견 제외를 맡는다. 물품/판매/등록 카탈로그를 바꾸지 않는다. `ExplorationRun`의 임시 발견은 `ExplorationOutcome` 안전 귀환·`SettlementResult`를 거쳐 후보 거점으로 합쳐진다. 실패 결과에는 새 보유 보상이 없고 이전 보유는 유지된다.
- `ProgressStore` 현행 쓰기 스키마는 **5**, 거점은 `harness_upgrades`를 포함한 **8필드**다. 구형 1~4의 빈 보유 목록과 기존 보완을 유지하며 읽기/실패한 쓰기는 원본 바이트를 보존한다. `GameEntry`는 구매 및 발견 정산 저장 성공 후 거점을 교체하고 다른 서비스/출정과 상호 배제한다.
- `HubUpgradePanel`은 보유·미장착 효과·구매 견적/확정·취소/실패 안내를 표시한다. `HubPanel`은 적용/미장착 개선, 결과 화면은 비금전 발견과 정산 시점을 표시한다. `hub_upgrade_smoke`는 구매·직접 발견/귀환·실패/재시도·새 실행·최소 복구의 앱 흐름과 위치/상태를 준비한 효과 경계를 구분한다. 기존 검사는 새 필드와 구형 자료만 갱신한다.

### DEV-0412의 휴대 도구 준비 검토 경계 — 미구현

- [검토안](../design/tool_preparation.md)은 소음 유인물 한 종류의 준비·수량·비용·적재·종료/반환 계약이다. 기존 도구의 투척·벽·청각 행동은 `gameplay/tools`와 현재 행동 규칙이 계속 소유한다. 가격·무료/추가 한도·개당 무게는 후속 준비 규칙 데이터로 분리하고 표시 문자열을 계산 근거로 삼지 않는다.
- `meta`는 추가분 재고·총수량 선택·부족분 구매 견적과 결제 후보, 출정 예약/시작·복구·반환의 검증 가능한 상태를 소유한다. 출정 중 소비/잔량은 `gameplay`, 번호와 최초 배정에 대한 종료 요약 검증은 정산 책임이다. 구매 재고와 무료 출정 수량을 하나의 영구 숫자로 합쳐 무료분이 누적되지 않게 한다.
- `core`의 출정/종료 데이터는 필요한 원시 수량과 독립 복사본만 전달하며 `data`/`meta` 가격 계산·파일 IO를 소유하지 않는다. Controller는 준비 수량을 한 번 받으며 공유 Resource의 `starting_uses`를 런 잔량으로 덮어쓰지 않는다. 역사적 단독 시험과 실제 앱 준비 수량을 명시적으로 구분한다.
- 무게 후보 적용 시 인벤토리에 도구 잔량의 외부 무게를 공개 계약으로 전달하고 기존 이동/소음 단계 계산을 재사용한다. UI가 무게를 더하거나 회수품 정의를 변조하지 않는다. 도구가 회수품 목록·보호 원본·판매/빠른 버리기로 흘러들지 않게 한다.
- `app`은 비활성 탐험 생성/검증→출정 예약 저장→상태 전환/초기화→시작 표식 저장→입력 활성화를 조정한다. 시작 전 기술 실패는 예약의 일회 복구로 처리한다. `infrastructure`는 검증된 후보를 저장하고 구형/손상 상태를 구분하며 도구 사용 규칙을 직접 판단하지 않는다.
- `ui`는 총수량 선택·무료/기존 추가분/부족분·실제 지출·적재·시작 후 종료와 복구 실패 안내를 표시한다. `tests`는 각 저장 전/후 재실행·실제 F 소비·귀환/실패/반환·무게/이동/소음·기존 서비스 보존을 검사한다. 이번 작업은 구조 계약만 기록하며 코드 파일·ID·저장 키/버전은 구현 착수 때 정한다.

### DEV-0413의 도구 준비·적재와 출정 저장 경계

- `LureSupplyRule`/`prototype_lure_supply.tres`는 무료/총량/재고 한도·가격·무게와 유효성 검사를 소유한다. 투척 거리/비행 등의 `NoiseLureRule`과 분리한다. `LurePreparationQuote`는 돈/재고/선택/규칙의 복사본으로 견적을 만들고 `HubState`가 확정 때 다시 대조한다. UI는 공개 견적을 표시한다.

- `ExpeditionLoadout`은 수량/단위 무게를 복사한다. `NoiseLureController.configure_supply()`는 한 번만 수량을 받고 기존 유효 투척에서 소비한다. `PlayerInventory.set_external_weight()`의 도구 무게를 공통 총량에 합산하고 기존 이동·소음·HUD가 같은 총량을 쓴다. 도구를 회수품 배열/분류에 넣지 않는다. `ExplorationOutcome`의 공개 사용 요약으로 결과 화면을 표시하며 반환 검증은 거점 도메인에서 한다.
- `HubLurePanel`은 총수량 선택·검토·확정/취소·오류 재시도를 표시한다. `GameEntry`는 다른 서비스/출정과 배타적으로 열고, 시작 기록 정리/복구 저장이 실패하면 모든 거점 변경을 막는다. 별도 테스트 저장소가 저장 경계/실패를 주입하며 출시 코드에는 시험 종료 훅을 넣지 않는다.

## DEV-0421 회수세 책임

[EconomyRule](../../src/data/economy_rule.gd)은 명시적 시험 요율과 유효성만 소유하며 Data에서 Meta에 의존하지 않는다. [RecoveryTax](../../src/meta/recovery_tax.gd)는 정확한 정수 세액·거래 근거/구형 모양 검증을 담당한다. SaleQuote와 SettlementResult는 판매 총액/요율/세금/입금을 복사하고 HubState는 현재 견적 재대조·후보 지갑/물품/비용 기록을 만든다. ExpeditionCosts는 거래별 실제 세금의 합·손익/현금/최근 보고를 검증하며 돈을 직접 움직이지 않는다.

ProgressStore는 스키마 9·거점 13필드·구형 1~8의 순서 있는 읽기 전환·정수 정규화·16 MiB 한도·원자적 교체를 담당한다. GameEntry는 저장 성공 뒤 상태 교체와 오래된 가격/세율의 재확인을 조정한다. 판매 UI와 CostReportText는 공개 견적/요약만 표시한다. [저장 계약](migration_changes.md#mig-chg-053-dev-0421-회수세-정산보고-연결), [시험 적용](../design/recovery_tax.md#dev-0421-회수세-시험-적용), [검사 기록](project_context.md#dev-0421-회수세-정산보고-연결-검사)을 따른다. 이전 스키마 6~8 절은 해당 작업 당시 이력이다.

## DEV-0422 휴대용 감정 구현 책임 인계

[휴대용 감정 수용 계약](../design/portable_appraisal.md#후속-구현-수용-기준)은 다음 DEV-0423의 설계 인계다. 이번 작업에서 새 클래스/상품 ID·필드/스키마를 추가하지 않는다.

- Data는 수량·가격·무게의 정의와 유효성, Core는 복사된 출정 구성/결과를 맡는다. Gameplay는 현재 가방의 실제 물품·감정 상태·잔량·사용·변경 이벤트를 다루며 Meta를 직접 참조하지 않는다.
- Meta는 도구 종류별 구매/예약/반환/소실·취득 원가·정산/의뢰·보고 후보를 검증한다. Infrastructure는 구형 1~9의 읽기 전환·손상 거절·원자적 저장을, App은 두 도구의 시작/종료·합산 무게와 저장 성공 뒤 상태 교체를 조정한다.
- UI는 현재 공개 정보·견적·대상 확인·결과를 표시하고 명령만 요청한다. 직접 물품을 감정하거나 잔량·돈을 바꾸지 않는다. 실제 대상/가방 변경·잔량·실행 시점을 재검증해 감정과 소비를 한 번 반영하며, 도구 간 원가·무게와 기존 영구 상태를 보존한다.

단가/한도/무게·일시정지 중 즉시 사용·저장 세부는 미적용 시험 제안이다. DEC-117의 승인 방향과 confirmed 아이템/경제·반복 탐험을 함께 읽고 Q-030의 후속 검증을 기록한다.

## DEV-0423 휴대용 감정 책임

[AppraisalSupplyRule](../../src/data/appraisal_supply_rule.gd)·[시험 정의](../../src/data/prototype_appraisal_supply.tres)는 가격/수량/무게를, [AppraisalPreparation](../../src/meta/appraisal_preparation.gd)·[견적](../../src/meta/appraisal_preparation_quote.gd)·HubState는 구매/배정/반환 후보와 구형 모양을 맡는다. [PortableAppraisalController](../../src/gameplay/tools/portable_appraisal_controller.gd)는 현재 물품/선택/정의/실행 여부를 대조해 PlayerInventory 감정과 잔량 감소를 관찰자 알림 전에 함께 처리한다. Gameplay는 Meta에 의존하지 않는다.

ExpeditionLoadout은 복사된 시작 수량/무게, ExplorationOutcome은 실제 사용 집계를 전달한다. PrototypeExploration은 두 도구 잔량 무게를 합산하고 도구 노드를 장면 준비 때 생성한다. InventoryPanel·[HubPortableAppraisalPanel](../../src/ui/hub_portable_appraisal_panel.gd)은 표시/확인 명령만 담당한다. ExpeditionCosts는 취득 원가/사용/반환/손실과 손익/현금을 검증한다. ProgressStore는 스키마10·15필드와 구형1~9 순차 보완·원자적 교체, GameEntry는 후보 저장 성공 후 상태 교체를 맡는다.

[저장 계약](../design/portable_appraisal.md#저장-모양과-전환)과 [검사 기록](project_context.md#dev-0423-휴대용-감정-연결-검사)을 따른다. 이전 스키마/미적용 절은 각 작업의 이력이다.
