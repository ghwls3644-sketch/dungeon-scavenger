# 폐던전 수색꾼 게임 스토리 문서 분할 및 관리 제안서

- 문서 버전: v0.1
- 문서 상태: 분할 실행 전 검토안
- 주 사용처: Codex 기반 문서 재구성, 이후 세계관·내러티브·게임 규칙 유지보수
- 기준 원본: `스토리 정리 v1.5(1).md`
- 관련 문서: `게임_개발_단계별_제안서_v0.1.md`
- 적용 범위: 문서 구조, 이관 절차, 변경 관리, 검수, Codex 작업 규칙
- 비적용 범위: 본 제안서만으로 원본 내용을 실제 분할하거나 설정을 새로 확정하지 않음

---

## 0. 제안 요약

현재 통합 문서는 세계관 원리, 플레이어 설정, 사회와 경제, NPC, 아이템, 내러티브 진행, 반복 탐험 규칙, 용어, 확정 변경점, 미결정 메모가 한 파일에 함께 들어 있다. 이 구조는 전체 맥락을 한 번에 보존하는 장점이 있지만, 다음 단계인 게임 기획과 Codex 구현 작업에서는 필요한 정보를 찾고 수정하기 어렵다.

따라서 다음 구조로 재편하는 것을 권장한다.

> **세계관의 사실은 `story`, 게임에서 작동하는 규칙은 `design`, 결정 이력과 미결정 사항은 `project`, 이전 통합본은 `archive`로 분리한다.**

분할 작업은 한 번에 내용을 고쳐 쓰는 방식이 아니라 다음 두 차례로 나눈다.

1. **1차 구조 이관:** 원문을 가급적 바꾸지 않고 책임별 파일로 옮긴다.
2. **2차 정합성 정리:** 중복을 제거하고, 기준 문서를 지정하며, 세계관과 구현 규칙을 분리한다.

중간 수정 가능성에 대비해 다음 안전장치를 함께 둔다.

- 분할 완료 전까지는 원본 통합본을 공식 기준으로 유지한다.
- 신규 분할 문서는 검토 완료 전까지 `draft` 상태로 둔다.
- 분할 중 새 설정 변경은 `migration_changes.md`에 먼저 기록한다.
- 단계별 검토 관문을 통과한 뒤에만 다음 단계로 이동한다.
- 최종 전환 시점에만 분할 문서를 공식 기준으로 승격한다.
- 원본은 삭제하지 않고 `archive`에서 읽기 전용으로 보존한다.
- 각 설정은 하나의 문서에서만 상세하게 정의한다.
- Codex는 전체 문서를 매번 읽지 않고, 중앙 색인에서 필요한 문서만 선택해 읽도록 한다.

이 방식의 목표는 단순히 파일을 작게 만드는 것이 아니다. **수정 범위를 예측할 수 있고, 설정 충돌을 추적할 수 있으며, 사람과 Codex가 같은 기준으로 작업할 수 있는 문서 체계**를 만드는 것이다.

# 1. 배경과 현재 문제

## 1-1. 통합 문서가 가진 장점

현재 문서는 다음 장점을 가진다.

- 설정의 전체 맥락이 한곳에 있다.
- 세계관과 게임 규칙이 왜 연결되는지 한 번에 확인할 수 있다.
- 수정 메모를 본문에 흡수한 이력이 남아 있다.
- 이전 버전과 비교하기 쉽다.
- 분할 과정에서 누락된 내용을 복구할 기준이 된다.

따라서 통합본 자체가 잘못된 것은 아니다. 문제는 프로젝트가 다음 단계로 넘어가면서 통합본을 **일상적인 작업 문서**로 계속 사용하기 어렵다는 점이다.

## 1-2. 현재 구조에서 예상되는 문제

### 탐색 비용 증가

특정 설정 하나를 확인하기 위해 긴 문서 전체를 검색해야 한다. 예를 들어 고유 유물의 원본성, 판매 가능 여부, 반복 등장 여부, NPC 반응, 방 변화 규칙이 서로 다른 장에 흩어져 있다.

### 중복 수정 위험

같은 개념이 여러 문맥에서 반복 설명된다. 한 부분만 수정하면 서로 다른 버전의 설정이 동시에 남을 수 있다.

### 세계관과 구현 규칙의 혼합

다음 두 종류의 문장이 같은 파트에 섞여 있다.

- 세계관 사실: “고유 유물은 특정 사건과 연결된 하나뿐인 원본이다.”
- 구현 규칙: “고유 유물은 한 번만 스폰되고 판매할 수 없다.”

첫 번째는 서사적 기준이고, 두 번째는 게임 시스템 정책이다. 둘을 분리하지 않으면 밸런스 변경이 설정 변경처럼 보이거나, 설정 변경이 코드 수정에 누락될 수 있다.

### 확정·가안·보류의 경계 약화

본문의 확정 설정과 각 장 하단의 검토 메모를 Codex가 함께 읽을 경우, 보류안을 현재 규칙으로 오해할 수 있다.

### 변경 영향 범위 파악 어려움

“마왕 관련 요소의 비중을 줄인다” 같은 변경이 세계 역사, NPC 지식, 발견물, 대사 톤, 메인 진행 중 어디에 영향을 주는지 한눈에 알기 어렵다.

### Codex 컨텍스트 과다

작은 기능을 구현할 때도 전체 통합본을 제공하면 관련 없는 설정이 함께 들어가 작업 집중도가 낮아진다. 반대로 문서 일부만 임의로 잘라 제공하면 필요한 제약을 놓칠 수 있다.

## 1-3. 해결해야 할 핵심 질문

문서 분할안은 다음 질문에 명확히 답해야 한다.

1. 특정 설정의 현재 기준은 어느 파일인가?
2. 세계관의 이유와 실제 게임 규칙은 어디에서 나뉘는가?
3. 아직 결정되지 않은 내용은 어디에 있는가?
4. 설정이 변경되면 어떤 문서를 함께 수정해야 하는가?
5. 분할 도중 새 변경이 생기면 원본과 신규 문서 중 어디에 반영하는가?
6. Codex가 작업별로 어떤 문서를 읽어야 하는가?
7. 분할이 완료되었다고 판단하는 기준은 무엇인가?
8. 누락이나 잘못된 재구성이 발견됐을 때 어떻게 복구하는가?

# 2. 목표와 비목표

## 2-1. 목표

- 사람이 5분 안에 필요한 설정 문서의 위치를 찾을 수 있다.
- Codex가 작업 주제에 필요한 문서만 선택적으로 읽을 수 있다.
- 하나의 설정은 하나의 기준 문서에서만 상세 정의된다.
- 세계관 사실과 실제 구현 규칙이 분리된다.
- 확정, 가안, 보류, 폐기 상태를 명확히 구분한다.
- 설정 변경의 이유와 영향 범위를 추적할 수 있다.
- 원본 통합본의 모든 내용이 누락 없이 이관된다.
- 중간에 설정이 수정되어도 이관 작업이 흔들리지 않는다.
- 분할 이후 게임 개발 제안서와 자연스럽게 연결된다.
- Git 이력과 문서 링크가 장기간 안정적으로 유지된다.

## 2-2. 비목표

이번 작업에서 다음은 하지 않는다.

- 세계관을 새로 확장하지 않는다.
- 미결정 사항을 임의로 확정하지 않는다.
- 경제 수치나 밸런스를 새로 계산하지 않는다.
- NPC 대사나 아이템 설명을 대량 작성하지 않는다.
- GDD 전체를 동시에 재작성하지 않는다.
- 실제 게임 코드나 데이터 파일을 생성하지 않는다.
- 원본을 삭제하거나 덮어쓰지 않는다.
- 분할과 문장 미화 작업을 한 번에 수행하지 않는다.

# 3. 문서 설계 원칙

## 3-1. 책임 기준으로 나눈다

기존 장 번호를 그대로 파일로 옮기기보다 **문서가 답하는 질문**을 기준으로 나눈다.

| 문서 영역 | 답해야 하는 질문 |
|---|---|
| Story | 세계관에서 무엇이 사실이며 왜 그런가? |
| Design | 플레이어에게 어떤 규칙으로 작동하는가? |
| Project | 무엇을 확정했고, 무엇이 미정이며, 왜 바뀌었는가? |
| Archive | 이전 시점에는 어떤 내용이 한 문서에 있었는가? |

## 3-2. 하나의 상세 정의는 한곳에만 둔다

예를 들어 폐던전의 정의와 소멸 원리는 `story/02_dungeon_canon.md`에서만 상세히 설명한다.

다른 문서는 필요한 만큼만 요약하고 기준 문서로 연결한다.

```markdown
폐던전은 코어가 파괴된 뒤 소멸 중인 던전이다.
상세 정의와 소멸 규칙은 [던전 정설](../story/02_dungeon_canon.md)을 따른다.
```

같은 설명을 여러 파일에 복제하지 않는다.

## 3-3. Story는 “왜”, Design은 “어떻게”를 담당한다

예시:

| 구분 | 문장 |
|---|---|
| Story | 고유 유물은 특정 사건이나 인물과 연결된 하나뿐인 원본이다. |
| Design | 고유 유물 획득 플래그가 저장되며, 획득 후 스폰 후보에서 제외한다. |
| Story | 수색꾼은 정면 전투보다 생환 판단에 강점이 있다. |
| Design | 위험 우회, 소음 관리, 퇴각, 짐 버리기 선택을 핵심 행동으로 제공한다. |
| Story | 폐던전은 자가 복구하지 않는다. |
| Design | 방문 간 변화는 복원형이 아니라 문 폐쇄, 붕괴, 오브젝트 노출로 표현한다. |

## 3-4. 요약 문서는 기준 문서를 대체하지 않는다

`README.md`와 `00_core_pillars.md`는 빠른 이해를 위한 문서다. 세부 설정의 최종 기준은 각 주제별 정설 문서에 둔다.

## 3-5. 상태를 문장 안이 아니라 문서 구조로 표시한다

확정과 보류를 같은 문단에서 섞지 않는다.

```markdown
## 확정 설정
잔재의 기억 흔적은 기본적으로 짧은 텍스트로 전달한다.

## 관련 보류 항목
환청·환시 연출 도입 여부는 `Q-003`을 참조한다.
```

## 3-6. 활성 문서 이름에는 버전을 붙이지 않는다

권장:

```text
02_dungeon_canon.md
```

비권장:

```text
02_dungeon_canon_v1.5.md
02_dungeon_canon_v1.6.md
```

활성 파일 이름은 고정하고, 버전은 Git 이력과 문서 메타데이터로 관리한다. 버전이 붙은 전체 사본은 `archive`에만 둔다.

## 3-7. 파일 수보다 탐색성을 우선한다

처음부터 너무 잘게 쪼개지 않는다. 하나의 파일이 다음 조건에 해당할 때만 추가 분할한다.

- 서로 다른 책임을 동시에 다룬다.
- 특정 주제를 찾기 위해 긴 검색이 반복된다.
- 수정할 때 관련 없는 영역까지 자주 건드리게 된다.
- 약 500줄을 넘어가며 하위 목차만으로 탐색이 어려워진다.

권장 크기는 대체로 150~350줄이지만, 이는 강제 제한이 아니라 읽기 편의 기준이다.

# 5. 파일별 역할

## 5-1. `docs/README.md`

프로젝트 문서 전체의 최상위 입구다.

포함 내용:

- 프로젝트 한 줄 소개
- 문서 영역별 설명
- 스토리 문서 진입 링크
- 게임 개발 제안서와 GDD 링크
- 현재 공식 기준 상태
- Archive 사용 금지 안내
- 변경 시 따라야 할 절차

이 파일에는 세계관 본문을 복사하지 않는다.

## 5-2. `story/README.md`

세계관·내러티브 문서의 중앙 색인이다.

포함 내용:

- 핵심 콘셉트 3~5문장
- 권장 읽기 순서
- 파일별 담당 범위
- 주제별 빠른 링크
- 확정·가안·보류 상태 설명
- 기준 문서 우선순위
- 관련 Design 문서 연결
- 현재 검토 중인 주요 질문 링크

Codex가 스토리 관련 작업을 시작할 때 가장 먼저 읽는 파일로 지정한다.

## 5-3. `story/00_core_pillars.md`

전체 설정과 기획이 흔들리지 않게 하는 1~2페이지짜리 핵심 제약 문서다.

포함 내용:

- 게임 한 줄 콘셉트
- 플레이어 정체성
- 핵심 플레이 감정
- 스토리의 역할
- 반드시 지킬 방향
- 피해야 할 방향
- 큰 설정 변경으로 간주할 조건

이 파일은 세부 설정을 담는 백과사전이 아니라, 하위 문서가 따라야 하는 헌장에 가깝다.

## 5-4. `story/01_world_history.md`

세계의 과거와 객관적 사실, 사회의 믿음을 분리해 관리한다.

포함 내용:

- 마왕 봉인
- 마왕과 던전 발생의 비인과 관계
- 던전 자연 발생
- 학계의 가설
- 모험가 시대의 시작
- 던전 산업의 형성 배경
- 마왕 관련 민간 전승
- 객관적 사실과 세계 내부 인식의 차이

권장 하위 구조:

```markdown
## 객관적 사실
## 학계의 가설
```

# 7. 기준 문서와 우선순위

## 7-1. 분할 완료 전

최종 전환 관문을 통과하기 전에는 다음 규칙을 적용한다.

1. `스토리 정리 v1.5(1).md`가 공식 기준이다.
2. 신규 분할 문서는 모두 `draft`다.
3. 분할 도중 발생한 새 변경은 `migration_changes.md`에 기록한다.
4. 승인된 변경은 원본에 먼저 반영하거나, 원본을 동결하기로 했다면 대기열에만 둔다.
5. 동일한 변경을 원본과 신규 문서에 무계획하게 이중 편집하지 않는다.

권장 방식은 **분할 작업 시작 시 원본을 동결하고, 새 변경은 대기열에 모은 뒤 1차 이관 완료 후 일괄 반영**하는 것이다. 긴급 변경만 예외로 한다.

## 7-2. 분할 완료 후

전환 관문을 통과하면 다음 규칙으로 바꾼다.

1. `story/`와 `design/`의 `confirmed` 문서가 공식 기준이다.
2. `00_core_pillars.md`는 하위 문서가 위반할 수 없는 상위 제약이다.
3. 세부 사실은 해당 주제별 정설 문서가 소유한다.
4. `decisions.md`는 변경 이유와 이력을 설명하며, 활성 문서와 반드시 일치해야 한다.
5. `open_questions.md`는 확정 설정을 덮어쓰지 않는다.
6. `README.md`의 요약이 세부 기준 문서와 충돌하면 세부 기준 문서를 따른다.
7. `archive/`는 절대 현재 기준으로 사용하지 않는다.

## 7-3. 충돌 발견 시

문서 사이에 충돌이 발견되면 Codex가 임의로 하나를 선택하지 않는다.

처리 순서:

1. 충돌 문장을 모두 표시한다.
2. 관련 결정 기록을 확인한다.
3. 어느 쪽도 명확하지 않으면 `open_questions.md`에 등록한다.
4. 임시 적용 원칙을 명시한다.
5. 승인 후 기준 문서와 관련 문서를 함께 갱신한다.
6. `document_changelog.md`와 필요 시 `decisions.md`를 갱신한다.

# 8. 문서 메타데이터와 작성 양식

## 8-1. 공통 Front Matter

각 활성 문서 상단에 다음 형식을 권장한다.

```yaml
---
id: STORY-DUNGEON-CANON
title: 던전과 폐던전 정설
status: draft
source_version: story-v1.5
last_reviewed:
owner:
related:
  - ../design/repeat_exploration.md
  - ../project/decisions.md
---
```

필드 의미:

| 필드 | 의미 |
|---|---|
| `id` | 파일명이 바뀌어도 유지되는 문서 식별자 |
| `status` | 문서의 현재 신뢰 상태 |
| `source_version` | 최초 이관 기준이 된 원본 버전 |
| `last_reviewed` | 마지막 전체 검토일 |
| `owner` | 최종 검토 책임자 또는 역할 |
| `related` | 반드시 함께 봐야 하는 문서 |

## 8-2. 상태 값

| 상태 | 의미 | Codex 사용 규칙 |
|---|---|---|
| `draft` | 이관 또는 작성 중 | 구현 기준으로 단독 사용 금지 |
| `provisional` | 임시 적용 중 | 명시된 범위에서만 사용 |
| `confirmed` | 현재 공식 기준 | 구현과 콘텐츠 작성에 사용 |
| `deprecated` | 더 이상 사용하지 않음 | 링크 추적 외 사용 금지 |
| `archived` | 과거 보존본 | 현재 기준으로 사용 금지 |

## 8-3. 권장 본문 구조

```markdown
# 문서 제목

## 목적
이 문서가 답하는 질문과 담당 범위

## 확정 설정
현재 공식 기준

## 세계 내부의 인식
객관적 사실과 다른 소문·오해가 있을 경우

## 게임 노출 원칙
플레이어가 어느 정도까지 알게 되는지

## 관련 구현 문서
Design 또는 GDD 링크

## 관련 결정과 미결정 사항
DEC/Q 링크
```

모든 문서에 모든 항목을 강제하지는 않지만, `목적`, `확정 설정`, `관련 문서`는 기본으로 둔다.

## 8-4. 결정과 질문 ID

- 결정: `DEC-001`, `DEC-002`
- 미결정: `Q-001`, `Q-002`
- 이관 중 변경: `MIG-CHG-001`
- 문서 작업 티켓: `DOC-0001`

ID는 한 번 발급하면 재사용하지 않는다.

# 9. 분할 실행 단계

## 단계 M0. 준비와 동결

### 목표

분할 작업 도중 원본이 변해 기준이 흔들리는 것을 막는다.

### 작업

- 원본 파일의 해시 또는 Git 커밋을 기록한다.
- 작업 브랜치를 만든다.
- 원본을 `archive/story_v1.5_full.md`로 복사한다.
- 아직 Archive 경고는 적용하지 않는다.
- `migration_manifest.md`와 `migration_changes.md`를 만든다.
- 원본의 모든 장과 소제목을 이관 대장에 등록한다.
- 분할 기간의 변경 처리 규칙을 확정한다.

### 권장 변경 정책

- 일반 설정 변경: `migration_changes.md`에 대기
- 긴급 오류 수정: 원본 수정 후 변경 ID를 발급하고 분할 대상에도 표시
- 문장 다듬기: 2차 정리까지 보류

### 검토 관문 G-M0

- 원본이 안전하게 보존되었는가?
- 모든 원본 소제목이 대장에 등록되었는가?
- 분할 중 변경을 어디에 기록할지 합의되었는가?
- 원본과 신규 문서 중 무엇이 현재 기준인지 명확한가?

## 단계 M1. 문서 골격 생성

### 목표

내용을 옮기기 전에 파일 책임과 탐색 경로를 확정한다.

### 작업

- 권장 폴더를 생성한다.
- 각 파일에 Front Matter와 목적 섹션을 만든다.
- `docs/README.md`와 `story/README.md`를 작성한다.
- 각 파일의 포함 범위와 제외 범위를 적는다.
- 관련 문서 링크 자리만 먼저 만든다.

### 이 단계에서 하지 않을 것

- 원문 문장 재작성
- 중복 제거
- 미결정 사항 확정
- 설정 추가

### 검토 관문 G-M1

- 각 파일이 답하는 질문이 겹치지 않는가?
- 특정 설정의 담당 문서를 바로 찾을 수 있는가?
- Story와 Design의 경계가 설명되어 있는가?
- 파일 수가 현재 규모에 비해 과도하지 않은가?

---

## 단계 M2. 1차 구조 이관

### 목표

원문의 의미를 바꾸지 않고 모든 내용을 대상 파일로 이동한다.

### 작업 원칙

- 원문 표현을 최대한 유지한다.
- 문장을 요약하거나 미화하지 않는다.
- 한 문장이 두 책임에 걸치면 우선 양쪽에 임시 복사하고 `중복` 표시를 한다.
- 각 이동을 `migration_manifest.md`에 기록한다.
- 각 장의 추가 검토 메모는 `open_questions.md`로 이동한다.
- 확정 변경점은 `decisions.md` 초안으로 이동한다.
- GDD 추천 목차는 `gdd_mapping.md`로 이동한다.

### 권장 작업 순서

1. 핵심 콘셉트와 톤
2. 세계 역사
3. 던전 정설
4. 플레이어와 사회
5. NPC와 세력
6. 아이템과 발견물
7. 내러티브 진행
8. Design 규칙 추출
9. 결정·질문·GDD 연결

### 검토 관문 G-M2

- 원본의 모든 소제목이 `moved` 이상인가?
- 누락된 표, 예시, 주의 문구가 없는가?
- 이관 과정에서 새 설정을 추가하지 않았는가?
- 원문 의미가 바뀐 문장은 별도로 표시되었는가?

---

## 단계 M3. 세계관과 구현 규칙 분리

### 목표

같은 주제를 설명하는 Story와 Design 문장을 책임에 맞게 나눈다.

### 작업

- 정확한 수치와 상태 전환은 Design으로 이동한다.
- 세계관상 이유와 금지 방향은 Story에 남긴다.
- Story에서 구현 세부를 제거하고 Design 링크를 단다.
- Design에서 장황한 세계관 설명을 제거하고 Story 링크를 단다.
- `gdd_mapping.md`에 양쪽 연결을 기록한다.

### 판별 질문

문장을 다음 질문으로 분류한다.

- “이 세계에서 왜 가능한가?” → Story
- “게임에서 언제, 어떤 데이터로 작동하는가?” → Design
- “왜 이 방향을 선택했는가?” → Decisions
- “아직 정하지 않았는가?” → Open Questions

### 검토 관문 G-M3

- Story를 읽으면 개연성을 이해할 수 있는가?
- Design을 읽으면 구현 행동을 판단할 수 있는가?
- 어느 한쪽만 수정해도 되는 항목과 함께 수정해야 하는 항목이 구분되는가?
- 수치와 밸런스가 Story에 불필요하게 남아 있지 않은가?

---

## 단계 M4. 중복 제거와 정합성 검토

### 목표

하나의 설정에 하나의 상세 정의만 남기고 상호 링크로 연결한다.

### 작업

- 핵심 용어를 전체 검색한다.
- 반복 설명의 기준 문서를 지정한다.
- 다른 파일의 반복 문장은 짧은 요약과 링크로 바꾼다.
- 서로 다르게 쓰인 정의를 비교한다.
- 충돌은 임의로 합치지 않고 결정 또는 질문으로 기록한다.
- 대기 중인 `migration_changes.md`를 승인된 순서대로 반영한다.
- 각 파일의 상태를 `draft`에서 `provisional`로 올릴지 검토한다.

### 필수 검색어 예시

- 마왕
- 던전 자연 발생
- 코어
- 범람
- 폐던전
- 잔여 구역
- 잔존 에너지
- 수색꾼
- 잔재
- 고유 유물
- 핵심 기록물
- 판매 불가
- 반복 등장
- 연구자
- 성직자

### 검토 관문 G-M4

- 각 핵심 용어의 상세 정의가 한곳에만 있는가?
- 서로 충돌하는 설정이 모두 해결되거나 질문으로 등록되었는가?
- 요약 문서와 상세 문서가 일치하는가?
- 관련 링크가 끊기지 않았는가?
- 분할 중 들어온 변경 요청이 모두 처리되었는가?

---

## 단계 M5. 최종 검수와 기준 전환

### 목표

분할 문서를 공식 기준으로 승격하고 원본을 Archive로 전환한다.

### 작업

- 모든 `migration_manifest` 항목을 `verified`로 만든다.
- 문서 링크 검사를 수행한다.
- 핵심 설정 체크리스트를 사람과 Codex가 각각 검토한다.
- `story/README.md`의 읽기 순서를 최종 확인한다.
- 활성 문서를 `confirmed`로 전환한다.
- 원본 Archive 상단에 경고를 추가한다.
- 저장소 루트의 `AGENTS.md`에 문서 탐색 규칙을 추가한다.
- 기존 개발 제안서의 기준 문서 링크를 새 구조로 갱신한다.
- 전환 커밋과 태그를 남긴다.

### 검토 관문 G-M5

다음 조건을 모두 만족해야 전환한다.

- 원본의 모든 내용이 추적 가능하다.
- 활성 문서에 미해결 충돌이 숨겨져 있지 않다.
- 미결정 사항은 `open_questions.md`에 분리되어 있다.
- 핵심 제약이 `00_core_pillars.md`에 반영되어 있다.
- Story와 Design의 상호 링크가 작동한다.
- Archive가 현재 기준으로 오해되지 않게 표시되어 있다.
- Codex 작업 규칙이 새 문서 구조를 가리킨다.

## 단계 M6. 운영과 후속 개선

### 목표

분할 이후 문서가 다시 거대한 통합본으로 돌아가거나 서로 어긋나는 것을 막는다.

### 운영 규칙

- 모든 설정 변경은 담당 기준 문서에서 시작한다.
- 큰 변경은 `DEC`를 먼저 작성한다.
- 미정인 제안은 본문이 아니라 `open_questions.md`에 둔다.
- 구현 규칙 변경 시 관련 Story 전제에 영향이 있는지 확인한다.
- 새 파일은 책임이 명확할 때만 추가한다.
- 분기별 또는 주요 개발 관문마다 정합성 검토를 한다.
- Archive는 참조만 하고 수정하지 않는다.

# 10. 중간 수정 대응 절차

분할 작업 중 설정 변경이 생길 가능성이 높으므로 변경 규모별 절차를 미리 정한다.

## 10-1. 소규모 변경

예: 표현 수정, 오탈자, 의미가 바뀌지 않는 문장 정리

처리:

1. 현재 기준 문서에 수정한다.
2. `document_changelog.md`에는 기록하지 않아도 된다.
3. 링크나 용어가 영향을 받는지만 확인한다.

분할 전이라면 원본을 직접 고치지 않고 2차 정리까지 보류하는 편이 안전하다.

## 10-2. 중간 규모 변경

예: NPC가 알고 있는 정보 단계 변경, 아이템 처리 정책 변경, 용어 통일

처리:

1. `MIG-CHG` 또는 `DEC`를 작성한다.
2. 영향 문서를 나열한다.
3. 기준 문서를 먼저 수정한다.
4. 관련 Design, GDD, 용어 문서를 갱신한다.
5. 링크와 예시 문장을 검사한다.
6. 변경 완료 상태를 기록한다.

## 10-3. 대규모 변경

예: 마왕과 던전의 관계 변경, 플레이어를 영웅형으로 변경, 반복 탐험 방식을 완전 절차 생성으로 변경

처리:

1. 바로 본문을 수정하지 않는다.
2. 별도 결정 제안서를 작성한다.
3. `00_core_pillars.md`와 충돌 여부를 확인한다.
4. Story, Design, GDD, 구현 영향표를 작성한다.
5. 승인 후 새 `DEC`를 발급한다.
6. 관련 문서를 한 작업 묶음으로 갱신한다.
7. 회귀 검토를 수행한다.

## 10-4. 분할 중 변경의 단일 대기열

분할 기간에는 모든 비긴급 변경을 `migration_changes.md`에 모은다. 이렇게 해야 다음 문제가 발생하지 않는다.

- 원본만 바뀌고 분할본은 오래된 상태가 됨
- 분할본만 바뀌고 원본 검증 기준과 달라짐
- 같은 변경을 서로 다른 문장으로 두 번 반영함
- 이관 누락과 실제 설정 변경을 구분하지 못함

# 11. 검수 전략

## 11-1. 누락 검수

- 원본의 모든 `#`, `##`, `###` 제목을 추출한다.
- 각 제목이 `migration_manifest.md`에 있는지 확인한다.
- 표, 인용문, 예시 대사, 추가 검토 메모를 별도로 확인한다.
- 원본에만 남은 핵심 용어 문장이 없는지 검색한다.

## 11-2. 중복 검수

핵심 용어별로 다음을 확인한다.

- 상세 정의가 두 파일 이상에 남아 있는가?
- 문구는 비슷하지만 의미가 다른가?
- 한 파일은 확정, 다른 파일은 가안으로 되어 있는가?
- 동일한 규칙이 Story와 Design에서 서로 다른 방식으로 적혔는가?

중복이 필요한 경우에는 한쪽을 요약으로 명시한다.

```markdown
> 요약: 폐던전은 자가 복구하지 않는다.
> 상세 원리는 `02_dungeon_canon.md`를 참조한다.
```

## 11-3. 정합성 검수

최소한 다음 관계를 점검한다.

- 마왕과 던전은 직접 인과가 없다는 전제가 모든 문서에서 유지되는가?
- 플레이어가 선택받은 영웅으로 바뀌는 표현이 없는가?
- 폐던전과 잔여 구역의 범위가 혼동되지 않는가?
- 코어 파괴 후 자가 복구가 중단된다는 규칙이 유지되는가?
- 반복 등장과 1회성 아이템의 구분이 일치하는가?
- 고유 유물과 핵심 기록물의 판매 정책이 일치하는가?
- 연구자의 지식이 처음부터 완성되어 있지 않은가?
- 마왕 떡밥이 핵심 진행을 강제하지 않는가?
- 던전 공포가 호러보다 탐험 긴장감으로 유지되는가?
- 거점은 지나치게 암울하지 않고 생활감이 있는가?

## 11-4. 링크 검수

- 상대 경로가 유효한가?
- 존재하지 않는 제목 앵커를 가리키지 않는가?
- Archive를 활성 기준처럼 링크하지 않는가?
- 순환 링크가 탐색을 방해하지 않는가?
- `README.md`에서 모든 활성 문서에 접근 가능한가?

가능하면 Markdown 링크 검사 도구를 CI에 추가한다.

## 11-5. Codex 이중 검수

동일한 Codex 작업에서 이관과 최종 검수를 동시에 맡기지 않는 편이 좋다.

권장 방식:

1. 작업 A: 원문을 대상 파일로 이동
2. 작업 B: 원본과 분할본의 누락 비교
3. 작업 C: 중복·충돌 검토
4. 사람 검토: 의미 변화와 최종 승인

서로 다른 작업 단위로 나누면 이전 판단을 그대로 정당화하는 오류를 줄일 수 있다.

# 12. 완료 조건

분할 작업은 파일이 생성되었다고 끝난 것이 아니다. 다음 조건을 모두 충족해야 한다.

## 구조 완료

- 권장 폴더와 활성 문서가 생성되어 있다.
- 각 파일의 목적과 책임이 명시되어 있다.
- 중앙 README에서 모든 문서로 이동할 수 있다.

## 이관 완료

- 원본의 모든 소제목이 이관 대장에 기록되어 있다.
- 모든 대장 항목이 `verified`다.
- 원본의 표, 예시, 메모가 누락되지 않았다.

## 정합성 완료

- 핵심 용어마다 단일 상세 기준 문서가 있다.
- 발견된 충돌은 해결되거나 질문으로 등록되어 있다.
- Story와 Design이 서로 다른 책임을 가진다.
- 확정과 보류가 분리되어 있다.

## 운영 준비 완료

- `AGENTS.md`가 새 문서 구조를 안내한다.
- 변경 절차가 문서화되어 있다.
- Archive 경고가 적용되어 있다.
- 개발 제안서와 GDD가 새 기준 문서를 참조한다.
- 원본으로 되돌릴 수 있는 Git 커밋이 남아 있다.

# 15. `AGENTS.md` 권장 문구

저장소 루트의 `AGENTS.md`에는 전체 세계관을 복사하지 않고 탐색 규칙만 짧게 둔다.

```markdown
# Story and design documentation

- 스토리 또는 설정 작업 전 `docs/story/README.md`를 먼저 읽는다.
- 모든 작업은 `docs/story/00_core_pillars.md`의 제약을 따른다.
- 작업 주제에 해당하는 Story 문서와 연결된 Design 문서만 추가로 읽는다.

- `draft`, `provisional`, `deferred` 내용을 확정 설정으로 가정하지 않는다.
- 설정을 바꾸기 전 `docs/project/decisions.md`와 `open_questions.md`를 확인한다.
- 세계관의 이유는 Story, 실제 작동 규칙은 Design에 기록한다.

- 충돌이 발견되면 임의로 해결하지 말고 보고하고 DEC 또는 Q로 등록한다.
- 문서 구조를 바꾸면 `document_changelog.md`를 갱신한다.
```

작업별 프롬프트에는 `AGENTS.md`를 반복해서 복사하지 말고, 관련 문서 경로와 완료 조건만 추가한다.

# 20. 최종 권장안

현재 통합본은 삭제하거나 단순히 장별로 잘라서는 안 된다. 다음 원칙으로 재구성하는 것이 가장 안전하다.

1. 원본을 먼저 보존하고 분할 기간 동안 기준을 명확히 한다.
2. 기존 장 번호가 아니라 문서 책임에 따라 Story, Design, Project, Archive로 나눈다.
3. 1차 이관에서는 내용을 고치지 않는다.
4. 2차 검토에서 중복을 제거하고 기준 문서를 지정한다.
5. 미결정 사항과 확정 결정은 본문 밖에서 ID로 관리한다.
6. 분할 중 새 변경은 단일 대기열에 모은다.
7. 최종 검수 전에는 신규 문서를 공식 기준으로 사용하지 않는다.
8. 전환 이후에는 원본을 Archive로만 유지한다.
9. Codex는 중앙 README에서 작업별 관련 문서만 읽는다.
10. 큰 변경은 핵심 전제, Story, Design, GDD에 미치는 영향을 먼저 검토한다.

권장 실행 순서는 다음과 같다.

> **원본 동결 → 문서 골격 → 내용 그대로 이관 → Story/Design 분리 → 중복 제거 → 변경 대기열 반영 → 누락·정합성 검수 → 공식 기준 전환 → 지속 운영**

이 구조를 사용하면 문서가 짧아지는 것뿐 아니라, 게임 구현 중 설정을 바꿀 때 **어디를 고쳐야 하는지, 무엇이 아직 미정인지, 어떤 규칙이 코드에 영향을 주는지**를 명확하게 추적할 수 있다.

# 부록 A. 전환 승인 체크리스트

## 원본과 이관

- [ ] 원본 파일이 변경 없이 보존되어 있다.
- [ ] 원본의 모든 장과 소제목이 이관 대장에 있다.
- [ ] 모든 표와 예시가 누락 없이 이관되었다.
- [ ] 각 이관 항목에 대상 문서가 기록되어 있다.

## 문서 구조

- [ ] `docs/README.md`에서 전체 문서 체계를 이해할 수 있다.
- [ ] `story/README.md`에서 주제별 기준 문서를 찾을 수 있다.
- [ ] 각 파일에 목적과 담당 범위가 있다.
- [ ] 파일 책임이 불필요하게 겹치지 않는다.

## 설정 정합성

- [ ] 핵심 전제가 `00_core_pillars.md`에 있다.
- [ ] 객관적 사실과 세계 내부의 믿음이 구분되어 있다.
- [ ] Story와 Design이 분리되어 있다.
- [ ] 핵심 용어의 상세 정의가 하나의 문서에만 있다.
- [ ] 미결정 사항이 본문에서 분리되어 있다.
- [ ] 결정 이력과 활성 문서가 일치한다.

## Codex 운영

- [ ] `AGENTS.md`가 새 문서 구조를 가리킨다.
- [ ] Archive 사용 금지 규칙이 있다.
- [ ] 작업 요청 양식이 준비되어 있다.
- [ ] 문서 링크 검사가 통과한다.
- [ ] 관련 문서만 읽는 작업 흐름이 검증되었다.

## 전환

- [ ] 모든 활성 문서가 검토를 통과했다.
- [ ] 모든 이관 대장 항목이 `verified`다.
- [ ] 분할 중 변경 대기열이 비어 있거나 명시적으로 이월되었다.
- [ ] 원본에 Archive 경고가 추가되었다.
- [ ] 분할 문서가 `confirmed`로 전환되었다.
- [ ] 기준 전환 커밋 또는 태그가 생성되었다.
